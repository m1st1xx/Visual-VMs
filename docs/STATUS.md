## Изменения после прогона 2 (финальное ревью)

- `Vmware.Run`: если по таймауту сам процесс уже завершился (каналы держит дочерний процесс VMware) — возвращается его код выхода, а не ошибка; `Win32Exception` при `Kill` перехватывается.
- «Выключить»: сначала `vmrun checkToolsState` (10 с); без запущенных Tools мягкое выключение не пробуется, сразу вопрос о принудительном. В вопросе — причина (гостевая ОС ещё выключается (60 с) / вывод vmrun), кнопка по умолчанию «Нет».
- Битая схема при запуске/открытии → ошибка, новая схема с облаком «Интернет»; при запуске `last.txt` удаляется.
- `.vvm`: пути ВМ — только полные локальные пути к `.vmx` (без UNC и `\?\`).
- `ApplyAsync`: при откате в ошибку дописываются пути, которые не удалось вернуть; удаляются оставшиеся `<vmx>.tmp`.
- «Удалить с диска»: пустая папка удаляется, только если её имя совпадает с именем vmx.
- Необработанное исключение до загрузки главного окна → сообщение и выход (не висящий процесс без окна).
- Предупреждение об открытом VMware дописывается к строке состояния, а не затирает ошибку.
- Значок приложения и окон, single-file publish, версия/Product в csproj.
- Эти изменения проверены юнит-тестами и сборкой, на настоящем VMware **не прогонялись**.

## Известные ограничения

- «Удалить с диска» не работает, пока ВМ открыта во вкладке VMware — вкладку нужно закрыть (программа подсказывает это в ошибке).
- В `inventory.vmls` после удаления ВМ остаются строки `indexN.*` (удаляются только `vmlistN.*`); VMware это не мешает.
- Откат `ApplyAsync` (восстановление уже записанных vmx) проверен только юнит-логикой и кодом — на реальных сбоях записи не проверялся.
- Пока открыт VMware GUI, он может перезаписать preferences.ini (имя сегмента пропадёт) и .vmx открытой вкладки. Программа предупреждает, но не блокирует.
- Не изменяются suspended, зашифрованные ВМ и файлы не в UTF-8 (в т.ч. с `.encoding` ≠ UTF-8).
- Максимум 10 адаптеров на ВМ (`ethernet0..9`).
- Сравнение пути в `inventory.vmls` — по тексту без учёта регистра (VMware хранит нормализованный путь).
- Если выключение нескольких ВМ отменено на второй, первая уже выключена.
- Сегмент, созданный для прямого соединения, остаётся в preferences.ini, если пользователь отменил операцию на шаге выключения.
- Сеть bridged / host-only / custom (VMnet) не отображается и не создаётся.

## Решения и почему

- **vmx — единственный источник истины для проводов**: схема не может разойтись с реальной конфигурацией; изменения, сделанные в самом VMware, видны после F5.
- **Свой построчный редактор вместо перегенерации файла**: VMware хранит в vmx много ключей, порядок и неизвестные строки сохраняются.
- **LAN segments (`pvn`), а не VMnet**: не требуют прав администратора и Virtual Network Editor; сегментов неограниченно.
- **Выключение только с согласия**: мягкое по умолчанию, принудительное — отдельным вопросом (без VMware Tools мягкое не работает, поэтому сначала проверяется `checkToolsState`).
- **Резервная копия один раз**: держит исходное состояние до программы, а не предыдущую правку.
- **`.vvm` недоверенный**: значения из него попадают в vmx/preferences.ini — проверка формата pvnID и запрет `"`/переводов строк закрывает инъекцию ключей; пути ВМ — только локальные `.vmx`.
- **Exe framework-dependent**: ~0,3 МБ вместо ~150 МБ self-contained; нужен .NET 8 Desktop Runtime.
- **Тесты не трогают хост**: только строки, временные файлы, `cmd.exe`.
